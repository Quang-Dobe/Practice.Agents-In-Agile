# `project/.claude/` — Project-tier LLM Wiki toolset

`project/.claude/` is the **project-tier** toolset, distinct from the root-tier `root/.claude/` crew kit. Where `root/.claude/` is installed to user scope and operates inside a single repository, `project/.claude/` is drop-copied to the **system root** that sits **one level above** many sibling repos and operates **across** all of them. It builds and serves a cross-repo "LLM Wiki": a `docs/memory/` store that summarizes and links back to (never duplicates) the knowledge already produced per repo — the root `docs/references.md` plus every sibling repo's `docs/narrative/` and `docs/domain/`. The `/wiki:ask` command then answers in-domain questions **inline in the main thread** (no sub-agent) from that wiki using a fixed, auditable retrieval order, falling through per-repo `docs/memory/` learnings then raw repo source as the last resorts, appending new source-read learnings to that repo's `docs/memory/`.

This tier also ships `/present:build`, a gate-free command that turns a feature's planning artifacts into a browsable HTML dossier at `docs/<feature>/present/`. It runs in **project mode** (grounds diagrams on `docs/domain/` + `docs/narrative/`) when either tree is present, or **root mode** (grounds on `docs/references.md` + `docs/memory/`) otherwise; project mode wins if both signal. See `## /present:build — feature dossier` below.

## Drop-copy instruction

Copy this `project/.claude/` folder **verbatim** (as `.claude/`) to the system root that contains your sibling repos. At that root it is the `.claude`-equivalent: a Claude Code session whose working directory is the system root will discover its commands, agents, and skills exactly the way a per-repo session discovers `root/.claude/`.

```powershell
# From the system root that contains repo-a/, repo-b/, ... and docs/
Copy-Item -Recurse .\path-to-scaffold\project\.claude .\.claude
```

## Drop-target layout

Once copied, the project tier operates against this layout. Everything except `docs/memory/` is **read-only input**:

```
<system-root>/
├── .claude/                         ← copy of this folder
├── docs/
│   ├── references.md                     ← GENERATED by wiki-architect (human fences preserved)
│   ├── references.diagram.excalidraw   ← GENERATED by wiki-diagrammer (hand-editable source of truth)
│   ├── references.diagram.svg / .png   ← GENERATED by wiki-diagrammer (svg is inlined, png is the preview)
│   ├── references-diagram.html         ← GENERATED at the command layer (dark page, human fence preserved)
│   └── memory/*.md                       ← root rollup (write target)
├── repo-a/docs/{narrative,domain,memory}/  ← narrative/domain read-only; memory written by /wiki:ask (T6)
├── repo-b/docs/{narrative,domain,memory}/  ← narrative/domain read-only; memory written by /wiki:ask (T6)
└── repo-c/ ...
```

Roles of the inputs and outputs:
- `docs/references.md` — cross-repo relationship overview; **generated** by the `wiki-architect` agent via `/wiki:enhance` (human `<!-- human:begin/end -->` fences preserved byte-for-byte).
- `docs/references.diagram.*` + `docs/references-diagram.html` — the picture of that overview; **generated** by `/wiki:enhance` step 9b. See `## /wiki:enhance — the architecture diagram` below.
- `docs/memory/*.md` — root rollup authored by the `wiki-bootstrapper`; the write target for summarize-and-link.
- `repo-*/docs/narrative/` — human-readable per-repo walkthrough (read-only input).
- `repo-*/docs/domain/` — Evans-canonical per-repo schema (read-only input).
- `repo-*/docs/memory/` — per-repo curated learnings; written by `/wiki:ask` on T6 source reads.
- repo source — last-resort ground truth, read only when every wiki tier above is insufficient.

## Conventions

- **Windows + PowerShell 7+.** Wherever shell is shown, use PowerShell idioms (`$null`, `$env:VAR`, backtick line-continuation).
- **Gate-free.** No `APPROVE` prompt on any write. The safety net for every write is append-only + same-source-ref dedup `(repo, path, line)` + `<!-- human:begin/end -->` fence preservation — not a gate.
- **Local filesystem paths only.** Remote inputs are refused: any path matching `^https?://` or `^git@` is rejected with a one-line message and the run stops.
- **No auto-commit.** This tier never commits on the operator's behalf.

## Boundary

The project tier is read-only against narrative/domain inputs and repo source. Its write targets are: the root `docs/memory/` (rollup), each repo's `docs/memory/` (router T6 learnings), `docs/references.md` (wiki-architect only), and the four diagram files (`wiki-diagrammer` owns the three `docs/references.diagram.*`; the command layer owns `docs/references-diagram.html`). No write lands elsewhere. The project-tier kit is also the single writer of the workspace-root `repo-layout.md` scan contract (`/wiki:bootstrap` drafts it, `/wiki:enhance` reconciles it); the crew agents (`project-explorer`, `project-overview`, `project-update`) are read-only on it and use it to scope their walks.

## `/diagram:build` — the system diagram

**Drawing is its own command.** `/wiki:*` decides what is true; `/diagram:build` decides what a
picture of it looks like. It reads `docs/references.md` and writes only diagram files, so you can
redraw at a different effort as often as you like without re-walking a single repo. `/wiki:enhance`
finishes by recommending it and listing the options.

```
/diagram:build [root-path] [--effort low|medium|high] [--html]
```

| Option | Default | Effect |
|---|---|---|
| `--effort low` | **yes** | request path, node classes, regions and their invariants. One render pass |
| `--effort medium` | | adds stores, model hosts, collectors, config keys, per-node detail, edge state |
| `--effort high` | | adds the map's own arguments — the gaps it found, the groupings it rejected |
| `--html` | off | also writes the SVG and a zoomable page |

No `docs/references.md` means no diagram: the command refuses rather than inventing a map.

| File | Owner | Written when | Role |
|---|---|---|---|
| `docs/references.diagram.excalidraw` | `wiki-diagrammer` | always | the drawing, and the render input. Kit-owned: open it at excalidraw.com to read or fork it, but it is regenerated, so save a fork under another name to keep hand edits |
| `docs/references.diagram.png` | `wiki-diagrammer` | always | the diagram. What the loop looks at, and what you share |
| `docs/references.diagram.svg` | `wiki-diagrammer` | `--html` | no background; inlined into the page |
| `docs/references-diagram.html` | command layer, `model: "sonnet"` per `[R-HTML-AGENT]` | `--html` | dark, theme-aware, self-contained, with a pan-and-zoom camera |

The SVG exists **only** to be inlined, so a bare run writes two files. The page inlines the SVG
rather than the PNG because a raster image softens the moment a reader zooms, and zooming is what the
camera is for.

### What the page shows

A row of boxes joined by arrows is not worth opening — a reader learns nothing from it that
`references.md`'s own bullet list does not already say. So the page carries the four things prose is
bad at:

| On the canvas | On the page |
|---|---|
| the request path, entry point to sink | the diagram, with wheel zoom, drag pan, Fit and 1:1 |
| **regions**, each labelled with the invariant that makes it a boundary | `## Boundaries` as a real `<table>` |
| **node classes** by shape — repo, ingress, store, external | |
| per-node detail: routes, owned stores, config keys | |

**Two slots, and that is the whole page.** Ownership, edge state and per-repo prose stay in
`references.md` — duplicating them here would give two places to go stale. Boundaries is the one
exception, as a real `<table>` rather than baked into the artwork, because its cells hold identifiers
and `file:line` references a reader needs to search and copy.

The page is **disposable output**: regenerated from scratch every run, with no human fence. A note
worth keeping goes in `references.md`, inside its own `<!-- human:begin -->` fence.

**Edge style is the legend**, so no key box: solid is asynchronous, dashed is a blocking call,
dotted leaves the system, and a faded arrow is `[planned]` — registered but on no request path.

The state markers are the part a hand-drawn diagram always gets wrong, and they are **derived from
code**, not judged by a human: `[fallback: Name]` comes from finding an `Unconfigured*` / `Stub*` /
`Fake*` / in-memory stand-in that absent config swaps in, so the edge is the difference between what
the system does and what it does when somebody forgot an environment variable.

### Derived, never invented

Every node is a repo, bounded context, or resource named in `references.md`. Every arrow is a
`## Context Map` line. Every region is a `## Boundaries` row. Every ownership line is an
`## Ownership` row. An arrow, box or label with nothing behind it is a bug, however good it looks. A
grouping with no invariant is **not** a boundary — it gets no box.

An empty context map is still a valid result: the repos are drawn side by side, unconnected, and the
subtitle says so.

Two skills drive it, in locked order: `wiki-diagram` (what to draw, where bytes may land) then
`excalidraw-diagram` (how it should look). The second is a **vendored** copy of
`coleam00/excalidraw-diagram-skill` with four changes, listed in its own
`## Vendored copy — what was changed` section. One of those four is not cosmetic: upstream's
`?bundle` import 404s on a transitive submodule, which hangs **every** render until Playwright times
out.

**Dependencies — the one place this tier is not zero-dep.** The render loop needs `uv` and a
Playwright Chromium, installed once per machine:

```powershell
Set-Location .claude/skills/excalidraw-diagram/references
uv sync
uv run playwright install chromium
```

Missing any of that → the `.excalidraw` is still written, the `.svg` / `.png` / `.html` are
skipped, one advisory line is printed, and the rest of the run continues.

**Idempotent by byte-compare.** A candidate `.excalidraw` equal to the file on disk means zero
renders and no HTML rewrite. A clean re-enhance costs no Chromium passes.

**Also note:** the tier already ships a second, unrelated diagram renderer —
`present-draw-diagram`, an inline-SVG renderer used by `/present:build`. The two do not
overlap: `present-draw-diagram` draws a **feature's** workflow into a dossier tab with no
dependencies; `excalidraw-diagram` draws the **system's** architecture into a hand-editable
file. Pick by subject, not by taste.

## `/present:build` — feature dossier

Given `<feature> [unit...]`, spawns the `present-builder` agent to render one `docs/<feature>/present/present-<unit>.html` per unit (`requirement`, `overview-plan`, `test`, `analyzed`, `plan`), then rebuilds the `present.html` index (tabs limited to units that exist). Diagram units (`overview-plan`, `plan`) additionally follow `present-draw-diagram`. Gate-free, idempotent (rewrites only changed bytes), fence-preserving. Refuses with a one-line message if neither project grounding (`docs/domain`/`docs/narrative`) nor root grounding (`repo-layout.md`/`docs/memory`/`docs/references.md`) is present.

## Who owns docs/memory/

`docs/memory/` is **co-owned** under a strict, asymmetric contract. The human is the curator/owner with full edit, curate, and delete authority. The agent is an append-only contributor: it may create new topic files and append new entries (gated by the same-source-ref dedup guard) but **never** overwrites or edits existing human or prior text. This asymmetry applies **only** to `docs/memory/` — `docs/narrative/` and `docs/domain/` remain fully agent-controlled. For the authoritative ownership table and the `<!-- human:begin --> / <!-- human:end -->` fence rules, see the `## Co-ownership contract` and `## Fence convention` sections in `skills/wiki-memory/SKILL.md`.

## `consumed_by` convention

Skill frontmatter declares the agents that load it using a **comma-separated scalar on one line**:

```yaml
consumed_by: /wiki:ask command, wiki-bootstrapper agent
```

Use this exact shape (one line, comma-separated, never a YAML list) for every skill in this tier.
